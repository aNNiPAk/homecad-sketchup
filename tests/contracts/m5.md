# M5 KitchenRun contract

Current composition behavior is specified additively in [M5.8](m58.md); it supersedes
the historical concept-only module internals described below.

M5 advertises `kitchen.run.v1`; protocol remains 1. The SketchUp Model is the Kitchen context. An applied `kitchen.run` is a root generated Group with stable HomeCAD UUID, schema version 1, revision 1, and canonical `kitchen_params_json`. Primitive tools may not edit generated Kitchen geometry.

M5.1 gives each semantic child a stable HomeCAD UUID. The run's canonical `semantic_objects` map stores `module:<key>`, `countertop`, `filler`, and `plinth` records with `homecad_id` and object revision. Generated child Groups use types `kitchen.base_cabinet`, `kitchen.wall_cabinet`, `kitchen.tall_cabinet`, `kitchen.appliance`, `kitchen.countertop`, `kitchen.filler`, or `kitchen.plinth`. The particular module type remains in `module_type` (for example `sink`, `hob`, or `fridge`). A module key identifies the same semantic object through regeneration; its UUID survives a type or dimension change, while its SketchUp persistent ID may change. Removed module keys return deletion tombstones. `find_objects(homecad_id)` and `get_object` resolve nested semantic children. Their `kitchen_run_id` and `wall_id` relationships are searchable metadata.

## Coordinates and inputs

`plan_kitchen_run` takes `wall` (an explicit unique target), `start_mm`, `end_mm`, `side` (`positive_v` or `negative_v`), and 1–32 ordered `modules`. Each module has a unique `key`, a `type`, `width_mm`, and optional `depth_mm`, `height_mm`, `bottom_mm`. The Wall U interval is `[start_mm,end_mm]`; offsets increase from the Wall start regardless of side. A run uses one tier:

| Tier | Types | Default depth / height / bottom (mm) |
| --- | --- | --- |
| base | `base_shelves`, `base_drawers`, `sink`, `hob`, `dishwasher`, `oven` | 560 / 720 / 100 |
| wall | `wall_shelves`, `wall_lift_front` | 350 / 720 / 1400 |
| tall | `tall_storage`, `fridge` | 600 / 2100 / 0 |

Other inputs: nonnegative `start_clearance_mm` and `end_clearance_mm` reserve space inside the requested Wall U interval; modules begin at `start_mm + start_clearance_mm` and cannot extend beyond `end_mm - end_clearance_mm`. Nonnegative `clearance_mm` offsets the run from the Wall face. `filler_max_mm` defaults to 150. `countertop` defaults true for base, `countertop_thickness_mm` defaults to 38, and `plinth` defaults true for base. Countertop/plinth are base-only. All lengths are public mm. Cabinet dimensions are generated geometry, never root scaling.

`constraints` supports `require_full_coverage` (default false), `require_countertop` (default true for base), nonnegative `min_opening_clearance_mm` (default 0), and optional positive `max_module_depth_mm`. Violations are structured plan conflicts. The generated end filler never consumes the reserved end clearance.

## Planning and mutation

`plan_kitchen_run` is read-only. It returns normalized `params`, current `wall_revision`, ordered `positions`, `filler_mm`, `remaining_mm`, `warnings`, structured `conflicts`, `units`, and a deterministic `fingerprint`. It checks Wall fit, the total width (negative filler), hosted opening/door/window/niche U/Z overlap, and same-side Wall attachments. An end filler is added only if the remaining gap is positive and at most `filler_max_mm`; a larger gap stays unallocated and is warned. Known Kitchen and Cabinet geometry is compared in U, Z, and depth. Unknown attachment geometry is checked conservatively by its projected U/Z bounds. It does not model door swing or appliance service clearances.

`apply_kitchen_run(plan)` recomputes the entire plan against the current SketchUp model, including Wall revision and collisions; changed/stale plans return `constraint_violation` before mutation. Plans containing conflicts cannot apply. One successful apply creates one `kitchen.run` root, generated concept modules, optional end filler, countertop and plinth, and maps to one SketchUp Undo operation. The mutation envelope lists the root first, followed by semantic children. A generation failure aborts the operation.

`validate_kitchen(target)` is read-only and checks the applied run against current cuts and attachments. `update_kitchen_run(target,changes)` accepts editable input fields except Wall identity and generated identity records, revalidates, preserves root/child UUIDs, regenerates geometry when needed, and increments the root revision once. Child revisions increment only when their own semantic descriptor changes. A name-only run update leaves child entities and revisions untouched; an unchanged normalized update opens no operation. `delete_kitchen_run(target)` returns pre-delete root/child tombstones and uses one Undo operation. Wall update relocates the run via the generic WallAttachment projection; an invalid Wall shortening is rejected before mutation, and Wall deletion requires cascade.

Collision checks use each generated module/countertop/filler/plinth U/Z/depth span. A same-side overlapping KitchenRun reports `appliance_collision`, `wall_cabinet_collision`, or `cabinet_collision` according to the involved semantic types. Hosted Wall cuts report `wall_cut_collision` with the cut type in the `other` field. Opposite Wall sides and non-overlapping vertical spans do not collide. Unknown WallAttachment kinds are checked conservatively.

## M5.2 service zones

Each module may add `service_clearance_mm` with nonnegative finite `u_start_mm`, `u_end_mm`, `front_mm`, `back_mm`, `top_mm`, and `bottom_mm`, each at most 5000 mm. Missing directions mean zero; a wholly zero object is omitted from canonical module parameters, preserving old runs. U start/end follow increasing Wall U on both sides. Front points away from the Wall, back toward it, and top/bottom are global Z. The module body spans U `[offset,offset+width]`, outward depth `[clearance,clearance+depth]`, and Z `[bottom,bottom+height]`. The service space is the expanded rectangular volume minus that body, decomposed into six face slabs. Mere touching within 0.01 mm is not an obstruction.

`plan_kitchen_run` remains read-only and returns at most 32 `service_zones` records (module key, normalized clearance and expanded U/outward/Z bounds) plus at most 100 `service_findings`. Each finding has `code=service_clearance_blocked`, `module_key`, `direction`, `object_id`, `object_type`, and optional `obstacle_key` for a sibling or another Kitchen module. New same-run modules have no HomeCAD ID before apply, so `object_id` is null and `obstacle_key` identifies them. By default findings also produce a summary warning and do not enter `conflicts`. With `constraints.require_service_clearance=true`, findings become blocking conflicts. If the result limit is exceeded, `service_check_incomplete` always blocks apply. `validate_kitchen` returns the same zone and finding structures after later scene changes. Apply/update recompute the entire plan before one Undo operation and return advisory warnings in the mutation envelope.

Spatial checks use world-space oriented rectangular volumes for HomeCAD Walls, Columns, Furniture Cabinets, and Kitchen modules/filler/countertop/plinth, including objects on neighboring Walls. Walls use the same occupied cells as their generated shell, so a through Opening/Door/Window and a Niche remove the appropriate obstacle volume. Same-run modules and filler count as obstacles; own countertop and plinth are intentional assembly parts and excluded. Cabinet and appliance concept envelopes are conservative. Room reference faces, hosted concept markers, primitive objects, and arbitrary SketchUp geometry are not checked. The check does not simulate opening fronts or infer regulatory clearances. Mutations in other domains may introduce a later obstruction; call `validate_kitchen` to detect it.

Existing Kitchen methods retain `kitchen.run.v1`; `kitchen.service_zone.v1` is additionally required when a plan/apply/update request uses the new module field or strict constraint. Old plans without them remain compatible with an older RBZ. Protocol version remains 1; M5.2 extension/package version is 0.7.1.

Generated appliances, sink, and hob are concept cabinet volumes with semantic module metadata. The initial Kitchen layer does not cut sink/hob holes, simulate appliances, build drawer mechanisms, or produce manufacturing specifications. Worktops are one straight slab per base run with aligned cabinet tops; mixed-tier and angled/corner runs require separate plans.

## Verification

`scripts/smoke_m5.py --confirm-disposable` runs only on a `HomeCADDev` marked disposable fixture. It plans, applies, validates, checks an adjacent-Wall service warning and strict rejection, frees the zone with Undo, checks a Door conflict, rejects invalid Wall shortening, confirms Wall relocation and Undo, captures an image, updates, undoes, and checks that all smoke IDs disappear. Use `scripts/dev_verify.py --milestone m5 --fast` during development and `--packaged` for acceptance. Both start a fresh owned SketchUp process. Standalone Ruby tests and CI cannot prove SketchUp kernel geometry or native Undo; packaged real SketchUp verification is required.

## M5.6 L-shaped variants

`plan_corner_kitchen_run` optionally takes `countertop` and `panels`. A missing `countertop` means `{enabled:false}`, preserving M5.5. With `enabled:true`, `thickness_mm` defaults to 38 and `first_end`/`second_end` are `{style:square}` or `{style:bevel,bevel_mm:positive}`. `cutouts` has at most 16 entries with unique `key`, `leg_key`, `offset_mm` along that Wall U, `front_mm` outward from its interior Wall face, and positive `width_mm` along U and `depth_mm` outward. All cutouts stay wholly within one arm with a 10 mm edge reserve; overlaps and excessive bevels are rejected before mutation. No diagonal fronts or arbitrary profiles are modeled.

`panels.first`/`panels.second` are optional end panel objects with positive `thickness_mm`, optional `material_id`, `grain_axis`, `sku`, and named `edge_band` sides (`length_start`, `length_end`, `width_start`, `width_end`). Each panel spans the leg's maximum module depth and cabinet height at its free end. A panel must fit inside the requested Wall interval. A shaped countertop produces one `shaped_panel` cutlist record with its polygon and cutouts; `manufacturing_status=concept_shaped` means the extents are not a fabrication-ready rectangular blank. End panels produce ordinary panel records. The semantic child UUID persists across updates; each variant update uses one Undo operation. Old one-Wall calls and old no-variant corner plans remain compatible with `kitchen.run.v1`/`kitchen.corner_run.v1`; new variant requests require `kitchen.variants.v1`. Protocol stays 1; package and extension are 0.11.0.
