# M0 protocol contract

Frame: `uint32_be length` + UTF-8 JSON object, 1..1,048,576 bytes.

Client first sends:

```json
{"jsonrpc":"2.0","id":1,"method":"hello","params":{"protocol_version":1,"client_version":"0.3.0"}}
```

Successful reply:

```json
{"jsonrpc":"2.0","id":1,"result":{"protocol_version":1,"ruby_extension_version":"0.3.0","capabilities":["model.info.v1","scene.inspect.v1","scene.measure.v1","view.capture.v1","scene.undo.v1"]}}
```

The capability array is additive to protocol version 1. Older bridges can omit it; `homecad_status` remains callable, while a method whose capability is absent returns `unsupported_operation`. The next request uses one supported bridge method, `params: {}` where applicable, and a distinct numeric `id`. A successful response uses the same `jsonrpc`, `id`, and `result` fields. The server closes the connection after that response. M0 methods are `homecad_status` and `get_model_info`; M1 methods are listed in [the M1 contract](m1.md).

Errors use JSON-RPC's `error` object: `{ "code": integer, "message": string, "data": { "category": string } }`. Codes: `-32600` invalid request, `-32601` unsupported operation, `-32602` invalid params, `-32603` internal error, `-32001` incompatible version. Local Python transport failures use category `connection_error`.

The JSON-RPC bridge is distinct from MCP stdio JSON-RPC. The Python server exposes exactly two zero-argument MCP tools, with the same names as the bridge methods.
