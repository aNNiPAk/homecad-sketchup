# M5.8 Kitchen composition contract (0.15.0)

Protocol stays 1. Existing tools, annotations and kitchen.run.v1/corner_run.v1/
variants.v1 remain. New optional module fields and straight cutouts additionally
require kitchen.composition.v1; old requests remain usable with old bridges.
An apply plan containing normalized composition_version=1 also requires it.

## One Furniture definition

KitchenCabinetDefinition maps canonical module parameters to Furniture validation,
construction geometry and part_schedule. No separately editable Furniture JSON is
stored on Kitchen children. Kitchen owns module:<key> (leg:<key>/module:<key> for
corners), semantic UUID/revision, kitchen_run_id and wall_id.

| Module | Furniture configuration |
| --- | --- |
| base_shelves / wall_shelves | carcass, one middle shelf by default |
| tall_storage | carcass, three shelves at quarter intervals |
| base_drawers | carcass, drawer fronts, two wooden drawers and two slide pairs |
| sink | open-top carcass, zero back by default; no plumbing |
| hob | open-top housing, no mounting details |
| oven | rectangular open-front housing, no mounting details |
| wall_lift_front | carcass and fixed concept front; no lift mechanism inferred |
| dishwasher / fridge | appliance volume, no counterfeit cabinet parts |

Existing hob/oven semantic types stay kitchen.appliance to preserve M6 sources.
Their cabinet parts are conceptual housings, not appliance manufacturing parts.
New requests snapshot panel_thickness_mm/back_thickness_mm/material_id/
front_material_id from project settings, explicit module values win. Sink's own
back=0 is a module configuration default. Reading/renaming legacy unversioned modules
does not inject fields, regenerate them or increment revisions. Explicit module
replacement upgrades its definition. Project settings changes do not silently
regenerate already snapshotted Kitchen modules.

Optional module fields: panel_thickness_mm, back_thickness_mm, shelf_z_mm, fronts,
drawers, drawer_layout, existing manufacturing/material identifiers. Shelves/fronts/
explicit drawers use Furniture Core schemas and bounds validation. Drawers and
drawer_layout cannot both be specified. All module dimensions remain the outer
envelope: derived carcass depth subtracts configured front thickness, ensuring
fronts stay inside the claimed collision/service volume.

drawer_layout fields: count=2 (1..16), gap_mm=2, side_thickness_mm=panel thickness,
base_thickness_mm=6, optional slide using the existing Furniture slide schema.
Default concept slide uses the existing generic HardwareCatalog family, unknown
SKU=null, nominal length equal to available case depth and side_clearance_mm=10.
These are HomeCAD concept defaults, not manufacturer or regulatory values.
Drawer Z ranges derive from its front and case panels; five-panel math, overlap/
shelf checks and purchased pair records belong exclusively to DrawerHardware.
Direct public Cabinet inputs retain their existing explicit-SKU requirement.
No rail geometry, drilling, mounting compatibility or motion is promised.

Cutlist uses the identical Furniture.part_schedule as generation; it only adds
run_id, module_key, module_type and semantic source_object_id. Manual hardware stays
separate from derived slide records, even for identical SKU. Unknown SKU/material
remain null. Zero back removes the panel and gives shelves full case depth.

## Straight countertop cutouts

plan_kitchen_run optionally accepts countertop_cutouts: up to 16 objects with unique
key, offset_mm, front_mm, width_mm, depth_mm. offset is Wall U; front is outward
distance from the Wall face (both placement sides). Width extends +U, depth outward.
Positive dimensions/finite coordinates, enabled base countertop, 10 mm edge reserve
and no overlap are required before mutation. No sink/hob type implies an automatic
cutout. Disabled tops reject nonempty cutouts. Empty list normalizes to absence.

Straight and L-shaped requests share normalization, rectangle bounds/overlap checks
and native inner-loop extrusion. L-shaped leg_key and beyond-corner limits remain.
Geometry kernel failure aborts the entire outer Kitchen operation. Straight shaped
tops produce concept_shaped cutlist records with explicit profile/cutouts, not a
fabrication-ready blank. Existing semantic countertop UUID survives changes;
descriptor change increments it once, name-only updates leave it untouched.

Normalized no-op opens no operation. Each Kitchen change uses one outer operation,
root revision +1; changed semantic children +1, unchanged children untouched. Cabinet
parts have no independently editable identity/revision. Locked/dependency/config/
cutout/conflict checks occur before operation. Appliance-only UUID/type survives
neighboring cabinet changes; removal/retype uses DomainHooks Consumer policy.

## Acceptance

Standalone bounds/schedule/cutlist tests cover every module type and zero back;
Python tests cover old RBZ rejection, schemas, forwarding and bridge results. Native
M5 smoke measures actual part bounds, two countertop hole areas, UUID/revisions,
invalid update, screenshots and Undo, alongside original service/Wall/Door checks.
Both M5 and M6 packaged verification are required; fake tests do not prove native
hole geometry. The focused M5 smoke also verifies the existing L-shaped hole's
native area after shared generator extraction, plus both legs' Furniture mapping.

Completed implementation verification on 2026-10-09: M5 fast, M5 packaged and M6
packaged passed on SketchUp 26.2.243 / HomeCAD 0.15.0. The latter checks Consumer
source preservation/retype lifecycle and Undo. Dev links were restored and cleanup
reported no errors. See M5 decisions for counts and visual review limitations.
