# M5.7 Hardware Core contract

M5.7 adds `furniture.hardware.v1` without changing protocol 1 or existing Cabinet requests. Package and Ruby extension version are 0.12.0. The original root `furniture.cabinet` and its HomeCAD UUID remain the mutation target. Drawers are canonical Cabinet parameters and generated parts, not independently editable SketchUp objects.

`list_hardware_catalog()` is read-only. The bundled JSON catalog has schema version 1 and currently declares only `homecad.wood_drawer.slide_pair.v1`, a generic HomeCAD assembly rule with purchase unit `pair`. It supplies no manufacturer SKU or mounting standard. `plan_cabinet_drawer(target, drawer)` resolves one root Cabinet, validates the proposed addition without editing it, and returns normalized drawer parameters, five panel records, one purchased slide-pair record, the current Cabinet revision and warnings. Plans are previews, not tokens for mutation; `update_furniture_object` revalidates the current Cabinet state.

`create_cabinet(drawers=...)` and `update_furniture_object(changes={"drawers": [...]})` accept at most 16 drawers. Each drawer requires a unique `key`, a distinct full-width Cabinet `drawer_front` identified by `front_key`, positive `bottom_mm`, `height_mm`, `depth_mm`, `side_thickness_mm`, and `base_thickness_mm`. `slide` requires the catalog `family_id`, caller-selected `sku`, positive `nominal_length_mm`, and positive per-side `side_clearance_mm`. All dimensions are millimeters in Cabinet local coordinates: X across width, Y from back to front, Z upward. The drawer outer width is `cabinet.width_mm - 2*cabinet.panel_thickness_mm - 2*slide.side_clearance_mm`; its front reaches the Cabinet front plane and its rear is `cabinet.depth_mm - drawer.depth_mm`. The five generated panels are base, left/right sides, back and front. The selected slide contributes exactly one purchase unit `pair` per drawer; no rail geometry, drilling or motion is modeled.

Validation checks the referenced front, cabinet and front Z ranges, case back and side clearances, available panel dimensions, shelf intersections, drawer overlap and slide nominal length. Invalid proposals return `constraint_violation` before opening an operation. A successful Cabinet mutation uses one `HomeCAD::Operation`, preserves root UUID, increments its revision once, and regenerates construction geometry. `concept` display detail does not generate drawer panels, but `list_furniture_parts` and `generate_cutlist` still derive identical records from parameters. Old Cabinets lacking `drawers` remain unchanged on read. Existing explicit `manufacturing.hardware` entries remain separate; callers must avoid listing the same purchased slide twice.

The cutlist has five `panel` records with stable `drawer:<key>/<part>` keys and one `hardware` record `drawer:<key>/slide_pair`, with `unit=pair`, `quantity=1`, the selected SKU and `front_key`. This is a preliminary schedule. Joinery, exact slide mounting, hole patterns, material suitability and manufacturer compatibility require project-specific verification. Vendor SKP geometry, DC formulas, HCG1 resources, prices and automatic hinge/lift selection are outside M5.7.

`scripts/smoke_m57.py --confirm-disposable` runs only on the dedicated `HomeCADDev` fixture. Acceptance uses `scripts/dev_verify.py --milestone m57 --packaged`, which builds and installs the current RBZ in a fresh owned SketchUp process and restores development links afterward.
