# M5.5 L-shaped KitchenRun contract

`kitchen.corner_run.v1` adds read-only `plan_corner_kitchen_run(legs,corner,name)`.
The existing `apply_kitchen_run`, `validate_kitchen`, `update_kitchen_run`, and
`delete_kitchen_run` operate on both legacy and L-shaped `kitchen.run` roots.
Old one-Wall requests and `kitchen.run.v1` remain compatible. An L-shaped plan carries
`layout_type=l_shaped` and requires the additional capability when applied.

There are exactly two ordered legs with distinct HomeCAD Walls. Each leg has a unique key,
explicit Wall target, requested Wall-U start/end, side, and 1..32 existing base module records;
both legs together are limited to 32 modules. Wall centerline endpoints meet within 1 mm;
the outward directions from that endpoint meet at 90° ±0.1°. Input leg order is
counterclockwise around the interior and each leg side faces that interior. Each interval
touches the shared endpoint. The corner consumes `span_first_mm` and `span_second_mm` at the
common end before regular modules start; these explicit positive spans must cover the other
leg's cabinet depth and half of its Wall thickness. Both legs have equal cabinet top elevations.
No inherited regulatory dimensions or clearance values are assumed.

`corner.mode=void` creates a semantic corner with two closed concept front panels.
`corner.mode=blind_cabinet` additionally requires `access_leg`; it creates one rectangular
concept blind cabinet with an access front on that leg. Hinges, drawer mechanisms, diagonal
fronts, and continuous worktop are not modeled in M5.5. Every generated module key is
`leg:<leg-key>/module:<module-key>`; the corner key is `corner`. Root and semantic child
HomeCAD UUIDs survive updates, while SketchUp child entity IDs may change.

The root stores two generic searchable Wall host IDs. Changing either Wall preflights the
whole L geometry; a valid change regenerates the run inside the Wall's single Undo operation,
increments the run revision once, and preserves root UUID. A change that disconnects the
Walls or invalidates a leg is rejected before mutation. Wall deletion requires `cascade=true`
and then deletes the dependent run in the same operation. Service zones on both legs remain
explicit; cross-leg and corner interference is reported, and strict mode blocks apply.
The planner is read-only, reports conflicts/warnings and a fingerprint, and `apply_kitchen_run`
replans before mutation. No U-shaped layout or multi-Wall simultaneous update is promised.
