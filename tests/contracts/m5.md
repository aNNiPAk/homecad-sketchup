# M5 KitchenRun contract

M5 advertises `kitchen.run.v1`; protocol remains 1. The SketchUp Model is the Kitchen context. An applied `kitchen.run` is a root generated Group with stable HomeCAD UUID, schema version 1, revision 1, and canonical `kitchen_params_json`. Module, worktop, filler, and plinth groups are generated children without separate public UUIDs. Primitive tools may not edit this geometry.

## Coordinates and inputs

`plan_kitchen_run` takes `wall` (an explicit unique target), `start_mm`, `end_mm`, `side` (`positive_v` or `negative_v`), and 1–32 ordered `modules`. Each module has a unique `key`, a `type`, `width_mm`, and optional `depth_mm`, `height_mm`, `bottom_mm`. The Wall U interval is `[start_mm,end_mm]`; offsets increase from the Wall start regardless of side. A run uses one tier:

| Tier | Types | Default depth / height / bottom (mm) |
| --- | --- | --- |
| base | `base_shelves`, `base_drawers`, `sink`, `hob`, `dishwasher`, `oven` | 560 / 720 / 100 |
| wall | `wall_shelves`, `wall_lift_front` | 350 / 720 / 1400 |
| tall | `tall_storage`, `fridge` | 600 / 2100 / 0 |

Other inputs: nonnegative `start_clearance_mm` and `end_clearance_mm` reserve space inside the requested Wall U interval; modules begin at `start_mm + start_clearance_mm` and cannot extend beyond `end_mm - end_clearance_mm`. Nonnegative `clearance_mm` offsets the run from the Wall face. `filler_max_mm` defaults to 150. `countertop` defaults true for base, `countertop_thickness_mm` defaults to 38, and `plinth` defaults true for base. Countertop/plinth are base-only. All lengths are public mm. Cabinet dimensions are generated geometry, never root scaling.

`constraints` supports `require_full_coverage` (default false), `require_countertop` (default true for base), nonnegative `min_opening_clearance_mm` (default 0), and optional positive `max_module_depth_mm`. Violations are structured plan conflicts. The generated end filler never consumes the reserved end clearance.

## Planning and mutation

`plan_kitchen_run` is read-only. It returns normalized `params`, current `wall_revision`, ordered `positions`, `filler_mm`, `remaining_mm`, `warnings`, structured `conflicts`, `units`, and a deterministic `fingerprint`. It checks Wall fit, the total width (negative filler), hosted opening/door/window/niche U/Z overlap, and same-side Wall attachments. An end filler is added only if the remaining gap is positive and at most `filler_max_mm`; a larger gap stays unallocated and is warned. The planner conservatively rejects projected overlap, even if the 3D solids might be separated in depth. It does not model door swing or appliance service clearances.

`apply_kitchen_run(plan)` recomputes the entire plan against the current SketchUp model, including Wall revision and collisions; changed/stale plans return `constraint_violation` before mutation. Plans containing conflicts cannot apply. One successful apply creates one `kitchen.run` root, generated concept modules, optional end filler, countertop and plinth, and maps to one SketchUp Undo operation. The result uses the shared mutation envelope. A generation failure aborts the operation.

`validate_kitchen(target)` is read-only and checks the applied run against current cuts and attachments. `update_kitchen_run(target,changes)` accepts editable input fields except Wall identity, revalidates, preserves root UUID, regenerates child geometry, and increments revision once. An unchanged normalized update opens no operation. `delete_kitchen_run(target)` returns a pre-delete tombstone and uses one Undo operation. Wall update relocates the run via the generic WallAttachment projection; an invalid Wall shortening is rejected before mutation, and Wall deletion requires cascade.

Generated appliances, sink, and hob are concept cabinet volumes with semantic module metadata. The initial Kitchen layer does not cut sink/hob holes, simulate appliances, build drawer mechanisms, or produce manufacturing specifications. Worktops are one straight slab per base run with aligned cabinet tops; mixed-tier and angled/corner runs require separate plans.

## Verification

`scripts/smoke_m5.py --confirm-disposable` runs only on a `HomeCADDev` marked disposable fixture. It plans, applies, validates, checks a new Door conflict, rejects invalid Wall shortening, confirms Wall relocation and Undo, captures an image, updates, undoes, and checks that all smoke IDs disappear. Use `scripts/dev_verify.py --milestone m5 --fast` during development and `--packaged` for acceptance. Both start a fresh owned SketchUp process. Standalone Ruby tests and CI cannot prove SketchUp kernel geometry or native Undo; packaged real SketchUp verification is required.
